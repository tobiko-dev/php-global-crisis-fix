# Reproducible product experiments

These are scripted experiments with fictional inventories. They test the engine, export, and command-line parts of a proposed agency workflow. They do not measure human task time, usability, customer demand, willingness to pay, remediation effectiveness, or security of a real deployment. The browser walkthrough is a separate source of evidence.

## Protocol established before the first run

The criteria below were written before running `scripts/test-hypotheses.mjs`. They are engineering acceptance criteria chosen for this prototype, not externally validated service levels. A failed criterion must be recorded in the results, not removed or adjusted to make a run pass.

| ID | Falsifiable hypothesis | Pass criterion |
| --- | --- | --- |
| H1 | An operator can represent the work from an initial observation to a customer handover without intermediate steps silently closing the item. | The upstream journey must produce verification needed → action required → verification needed → verification needed → evidence complete. The vendor journey must produce verification needed → provider confirmed → verification needed after a later lower-version web observation → provider confirmed after renewed confirmation. JSON export/import must preserve the final inventory and recompute the same outcomes. |
| H2 | A customer handover generated from a multi-customer inventory contains only that customer's recorded environments. | Both the HTML and CSV exports must include the two selected environments, omit every unique marker from the other two customers, and retain the demonstration label. HTML must contain exactly two environment cards; CSV must have two data rows. The mixed source inventory must remain unchanged. |
| H3 | Recorded positive outcomes stop being current when evidence or the advisory catalog expires. | With unchanged input, moving the clock more than 72 hours forward must remove both positive outcomes. In a separate pair with fresh evidence on both sides of catalog expiry, evidence complete and provider confirmed must become verification needed immediately after expiry. |
| H4 | The import limits reject an oversized handover without destroying the source inventory or an earlier good report. | A representative 1,000-environment fleet below 5 MiB must be accepted by the API and CLI. A 1,001-environment fleet and a 1,000-environment fleet over 5 MiB must be rejected for the expected limit, leave source file hashes unchanged, produce no output file, and leave the earlier valid report unchanged. |
| H5 | The local engine can produce a handover at the advertised inventory limit within explicit prototype latency budgets. | For each of 10, 100, and 1,000 mixed environments: 25 measured samples after 3 warmups; assessment p95 ≤ 2,000 ms; HTML plus CSV export p95 ≤ 5,000 ms; input < 5 MiB; stable counts, output bytes, and output hashes across samples. |
| H6 | A version-only spreadsheet rule misses information used by the evidence workflow. | On the published, deliberately selected comparison cases, find at least one case that the baseline would close while the product requires verification, and at least one lower-version case where the baseline calls for an update while the product requires backport/provider clarification. Publish every case and the baseline rule. |

H6 is a demonstration of different decision rules on selected examples. It is not an accuracy comparison with skilled operators or existing spreadsheets, and its disagreement rate must not be presented as a population error rate or time saving.

## How to reproduce

Use Node.js 20 or later. No packages, network access, production access, or credentials are needed.

```sh
node scripts/test-hypotheses.mjs --out reports/experiments-recheck
```

Choose a new output directory for each run. The runner refuses to overwrite one. With no `--out`, it creates a timestamped directory under `reports/`. Exit `0` means every declared criterion passed; exit `1` means a criterion or the runner failed. The JSON result includes failures as well as successes.

The runner writes the machine-readable results, all operator stages, the comparison cases, the final fictional inventory, a customer HTML report, and its CSV counterpart. Boundary tests use temporary files that are removed after the run. A 1,000-environment fixture is also saved so the measured input can be inspected. The larger rejected files are reproducibly generated by the script rather than checked into Git.

## Method and interpretation

### Operator and customer workflows

The self-managed journey begins with a CLI observation of an old upstream version. A web-runtime observation then establishes that an update is needed. Recording an installed update still leaves verification open; recording a restarted, fixed web runtime leaves the application check open; the subsequent check completes the recorded evidence.

The managed-hosting journey starts with an ambiguous vendor build. A named operator records a specific provider assertion for both catalog CVEs. A newer web observation with the same lower upstream version prefix reopens backport clarification. Renewing the provider assertion for the observed build resolves that assertion again. This never becomes independent runtime verification.

These transitions are simulated data entry through the same exported engine used by the UI. They do not run PHP, restart workers, contact a provider, test a live application, or verify that an entered statement is true. The final records deliberately identify themselves as fictional examples.

The customer-isolation experiment combines the two selected environments with records for two other fictional customers. Unique markers appear in their names, notes, provider details, references, and reviewer fields. It inspects the complete HTML and CSV strings, not just the visible page, and parses the CSV to count records. This checks the supplied cases; it does not prove isolation for every possible input or add access control to the local application.

### Time controls

The principal assessment clock is `2026-10-22T12:00:00Z`. The age test advances that clock by 73 hours without changing the observations. The catalog boundary test uses the same fresh observations at `2026-10-28T23:59:58Z` and `2026-10-29T00:00:00Z`.

The explicit clock is supplied by the experiment runner, not imported from a report. Ordinary exports use the current clock. The saved fictional HTML report has a simulated generation time for reproducibility and is not evidence that those deployments existed.

### Scale workload

Each size repeats a deterministic ten-environment mix containing all four outcomes: old upstream web runtime, fixed CLI runtime, installed update, incomplete web evidence, complete upstream evidence, uncertain vendor build, provider assertion, later vendor observation, unknown runtime with a provider assertion, and stale evidence. Every environment has a unique ID; customer groups repeat across 20 fictional accounts at the largest size.

Assessment includes normalization and evidence evaluation. Each HTML and CSV export is timed separately and includes its own normalization and reassessment, as the public export API requires. The combined export time is the sum of those two durations. Output encoding, hashing, file writes, subprocess startup, browser rendering, printing, and operator work are outside these timed intervals. The CLI boundary experiment is separate.

The runner uses `performance.now()`, three unmeasured warmup iterations, and 25 recorded iterations per size. Median and p95 use the nearest-rank definition on the individual samples. The JSON retains every timing sample and reports minimum and maximum values. The 2-second assessment and 5-second combined-export budgets were selected before measurement as generous local prototype gates. They are not a promise for every machine. Measurements come from a shared execution environment, not dedicated or controlled hardware; CPU scheduling, thermal state, browser performance, and concurrent workloads are not controlled. There is no forced garbage collection and no confidence interval or population estimate.

### Constructed spreadsheet baseline

The baseline extracts a leading numeric `major.minor.patch`, finds the branch minimum in the same catalog, and labels versions at or above it **close item**, lower versions **update**, and unrecognized versions **unknown**. It ignores distribution, runtime source, dates, restarts, application checks, reviewers, and provider assertions. Its complete source and inputs are published in the runner and comparison JSON.

Product statuses are also retained in full. For comparison only, evidence complete and provider confirmed map to **close item**, action required maps to **update**, and verification needed maps to **unknown**. Mapping provider confirmed to closure in this table does not equate it with independent verification. A policy disagreement is not evidence of exploitation, vulnerability, or an incorrect human decision.

## First-run results

**All 15 declared engineering checks passed across the six hypotheses.** The run took place on 2026-10-22 from 03:58:33 to 03:58:42 UTC. The protocol and source hashes, every check, every timing sample, and all output sizes are preserved in [the raw result](../examples/experiments/run-2026-10-22/results.json). The criteria above were not adjusted after measurement.

This supports the tested engine/export workflows on synthetic inputs. It does not establish that an agency wants this product or can complete the real operational work faster.

### What the baseline actually demonstrates

The [complete comparison](../examples/experiments/run-2026-10-22/baseline-comparison.json) publishes all 15 inputs and both outcomes. Eight selected records had a sufficiently high numeric version but still needed verification: CLI-only evidence, an installed package, no restart confirmation, no application check, no reviewer, stale evidence, a prerelease, and an unconfirmed vendor build. Two lower-version vendor records needed clarification instead of an inferred update decision. Two further disagreements involved provider assertions that the numeric-only baseline cannot represent. Three cases agreed under the comparison mapping.

These examples show why distribution, observation source, evidence age, operational checks, and provider statements can matter to the workflow. Because the cases were deliberately chosen to expose differences, **12 of 15 is not an error-rate estimate for real agencies**. A competent operator or a spreadsheet with equivalent evidence columns may already make the same distinctions. This experiment does not compare against that stronger alternative.

### Negative findings and unresolved value claims

No declared engineering criterion failed in this run, and no new product defect was discovered. Several useful limits were directly visible:

- A valid record count was insufficient for import: the 1,000-environment file with long, individually permitted evidence fields exceeded 5 MiB and was rejected. Operators still need a manageable evidence inventory.
- The provider workflow closed an assertion based only on fictional, operator-entered statements. That is the designed trust boundary, not proof that any system was patched. The experiment cannot validate those statements.
- A current-looking version alone was insufficient for many selected records, so an operator still has to gather missing evidence. No reduction in the work of obtaining that evidence was measured.
- The 1,000-environment report exceeded 1.3 million bytes. Generating it quickly does not establish that a customer would read it or that a single report of that length is a useful deliverable; exact customer filtering addresses a different, narrower need.
- Positive evidence aged out as intended, so maintaining an apparently complete inventory requires renewed observations and catalog review. The experiment did not measure the cost of that maintenance.

Keep the existing correctness suite as the continuous-integration gate. Run this measurement script explicitly when reviewing the product hypotheses; its machine-dependent latency criteria should not become mandatory performance gates on arbitrary CI hardware. [Browser capacity measurements](CAPACITY.md) test a different part of the workflow and should be interpreted separately.

## Known gaps to carry into a pilot

- No agency or customer participated in these experiments. No human task completion, comprehension, report acceptance, time saving, price acceptance, or repeated need was measured.
- Operator-entered statements and provider references are not authenticated. Correctly formatted fictional assertions can produce a positive recorded outcome by design. The application does not prove that patching happened.
- The performance workload uses ordinary-sized evidence notes. Inventories with much longer fields can reach the 5 MiB limit before 1,000 environments. The 1,000-environment limit is not a guarantee that every possible 1,000-environment JSON file fits.
- Engine and export timings do not establish that a 1,000-card dashboard is comfortable to use or that a very long report is readable. Browser interaction and printing need separate evaluation.
- Selected markers and workflow paths give bounded regression evidence, not a security audit or proof of all possible data isolation cases.
- A hand-maintained, expiring catalog creates an ongoing maintenance obligation. These experiments do not supply an update service, incident response, or deployment changes.
